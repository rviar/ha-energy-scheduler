# Динамический PV Confidence: probabilistic baseline + внутридневная коррекция

## Контекст

`pv_confidence_factor` — статичный ползунок 50–100% в настройках, применяется как плоский множитель к прогнозу PV в `optimizer.py:380` и `optimizer.py:732`. На практике прогноз Solcast/Forecast.Solar может расходиться с фактом в разы за один день (наблюдённый кейс: прогноз 22.98 kWh, факт 9.7 kWh — расхождение 58%), и статичный множитель не реагирует на это.

При исследовании выяснилось, что Solcast уже выдаёт собственные процентили (`pv_estimate10`/`pv_estimate`/`pv_estimate90`) и per-period `confidence` (в `analysis.intervals`). В кейсе 22.98→9.7 факт лёг ровно в P10 (`estimate10: 9.7945`) при `analysis.confidence: 0.2861`. Solcast сам сигнализировал низкую уверенность — мы просто использовали медиану и игнорировали этот сигнал.

## Решение

Вводим **двухслойную модель**: probabilistic baseline (превентивно с рассвета) + внутридневная реактивная коррекция (поверх baseline).

### Слой 1 — Probabilistic baseline (Solcast P10/P50/P90)

Для каждого периода прогноза:

```text
baseline_kwh = pv_estimate10 + confidence * (pv_estimate - pv_estimate10)
```

- `confidence = 1` → baseline = P50 (Solcast уверен, доверяем медиане).
- `confidence = 0` → baseline = P10 (Solcast не уверен, страхуемся пессимистично).
- Промежуточные значения интерполируются линейно.
- Используется **per-period** `confidence` из `analysis.intervals[]` (не daily `analysis.confidence`). Это даёт разную консервативность для разных часов — например, утренний слот с высокой confidence получит P50, а полуденный с низкой — близко к P10.

Этот baseline заменяет сырой `pv_estimate` во всех расчётах оптимизатора.

**Калибровка формулы.** Линейный blend намеренно даёт сильно консервативный baseline в дни высокой неопределённости. Реальный пример (2026-05-09, `analysis.confidence: 0.057`, P10=3.29 kWh, P50=29.84 kWh): baseline = 3.29 + 0.057 × 26.55 ≈ **4.80 kWh** (в 6 раз ниже P50). Это намеренное поведение — асимметрия потерь делает консервативный план дешевле в среднем (избыточный импорт из сети дороже чем упущенный экспорт), а слой 2 поднимет план в течение дня если Solcast переоценил неопределённость. Если на практике формула окажется слишком пессимистичной, рассматриваем замену на `sqrt(confidence)` или introduce floor `max(P10, climatology)` — это однострочная правка.

### Слой 2 — Внутридневная реактивная коррекция

На каждом запуске оптимизации:

```text
factor_today = clamp(actual_today / baseline_for_elapsed_pv_on_hours, 0.3, 1.5)
```

применяется к baseline для **оставшихся часов сегодняшней даты**. Часы других дат используют только baseline (без factor_today).

### Fallback для не-probabilistic провайдеров

Solcast — единственный из поддерживаемых сейчас источников, который публикует P10/P90 и per-period confidence. Forecast.Solar, OpenMeteo, weather-based интеграции и кастомные сенсоры дают только точечную оценку. Если парсер не находит `pv_estimate10`/`pv_estimate90` для периода — соответствующие поля = `None`, формула baseline вырождается в `baseline = kwh` (используем точечную оценку). Слой 2 (реактивная коррекция) работает идентично для всех. Слайдер `pv_confidence_factor` применяется как дополнительный мультипликатор поверх всего и для не-probabilistic пользователей остаётся главным рычагом консервативности.

Не-Solcast пользователи относительно текущего поведения **только выигрывают** — получают реактивную коррекцию, которой сейчас нет, без потери ручного контроля через slider.

### Ключевые правила

- **Источник факта** — текущее `state` пользовательского `today_production` сенсора (сбрасывается в полночь, история не нужна). Считывается с валидацией: `unknown`/`unavailable`/NaN/отрицательные значения отключают динамику с причиной `sensor_invalid`. Единица измерения проверяется через атрибут `unit_of_measurement` и приводится к kWh (Wh/MWh поддерживаются).
- **Источник прогноза для прошедших часов** — `PVForecastParser` читает `detailedHourly` без фильтра прошедших часов (атрибут содержит все 24 часа сегодня). Снапшот утреннего прогноза не делаем — для v1 принимаем небольшое смещение от пост-хок уточнений Solcast.
- **Слайдер `pv_confidence_factor`** остаётся как дополнительный мультипликатор поверх baseline. Default 100%. Полезен для Forecast.Solar пользователей и для тех, кто хочет ручную тонкую настройку поверх Solcast P10/P50.
- **Знаменатель** — сумма прогноза за уже прошедшие часы сегодня, **исключая часы где `inverter_pv_input_switch` физически был OFF** большую часть часа. Источник истины — история состояний свитча из HA recorder (`history.get_significant_states` за сегодня, один запрос на пересчёт). Это критично: в режимах `paid_import` и `charge` с отрицательной ценой PV искусственно отключается (`schedule_executor.py:507-522`), и наивное сравнение факта с прогнозом дало бы фиктивно низкий коэффициент. Если свитч не сконфигурирован — все прошедшие часы считаются включёнными. Если recorder недоступен или history-запрос падает — fallback на «все прошедшие часы включены» с логом warning.
- **Порог активации** — 2 kWh накопленного прогноза за прошедшие солнечные часы. Ниже порога используется статичный ползунок (защита от утреннего шума).
- **Clamp [0.3, 1.5]** симметрично — защита от выбросов сенсора и от чрезмерно жадного планирования при коротком ярком окне.
- **Только сегодня, остаток дня** — не применяем today_factor на завтра+, чтобы сегодняшняя облачность не отравляла завтрашний план.

## Рассмотренные альтернативы

- **Использовать только сырой P50 (текущее поведение) с реактивной коррекцией.** Отклонено: Solcast уже сообщает о неуверенности через `analysis.confidence`, игнорировать этот сигнал и узнавать о промахе только постфактум через A — потеря информации. Сегодняшний кейс (P50=22.98, факт=9.7=P10) показал что превентивный слой важнее реактивного утром.
- **Использовать только P10 как baseline (без blending'а).** Отклонено: чрезмерно консервативно в дни когда Solcast уверен (`confidence ≈ 1`). Линейная интерполяция P10↔P50 по confidence даёт корректное поведение в обоих режимах.
- **Использовать `schedule.pv_input` из storage_manager вместо истории свитча.** Отклонено: расписание отражает намерение, а не факт. Расходится с реальностью при свежей установке (расписания за прошлые часы нет), ручных переключениях свитча и сбоях `schedule_executor`. История свитча даёт ground truth ценой одного recorder-запроса, что приемлемо.
- **Долгосрочный множитель по recorder-истории за 14–30 дней.** Отклонён как первый шаг: не лечит конкретный аномальный день (как наблюдённый кейс), требует storage и истории, а большинство выгоды получаем уже от внутридневного фактора. Может быть добавлен позже отдельным слоем.
- **Полная замена статичного ползунка.** Отклонена: ползунок остаётся полезным как fallback (пока порог 2 kWh не достигнут) и как множитель для будущих дней, где никакого факта ещё нет.
- **Применение today_factor на весь горизонт 12–48ч.** Отклонено: погода между днями некоррелирована достаточно, чтобы это создавало больше ошибок чем решало.
- **Фактор только в downside (max=1.0).** Отклонён в пользу симметричного clamp — если факт обгоняет прогноз, не использовать бонусное солнце было бы такой же ошибкой как не учесть тучу.

## Последствия

- Появляются два новых параметра конфигурации: `pv_production_sensor` (entity selector) и `pv_dynamic_correction_enabled` (bool).
- `PVForecastParser` расширяется: парсер Solcast возвращает `{kwh, kwh_p10, kwh_p90, confidence}` для каждого периода (раньше только `kwh`). Для не-Solcast форматов остальные поля = `None`.
- Появляются новые методы парсера: `get_today_baseline_forecast()` и `get_baseline_forecast(hours_ahead)`, которые применяют blend P10+conf×(P50−P10) и возвращают «эффективный прогноз» для оптимизатора.
- Внутри оптимизатора скаляр `pv_confidence_factor` уступает место per-hour helper'у — все места применения должны учитывать дату/час и работать с baseline вместо сырого forecast.
- В сенсор расписания добавляются атрибуты для observability: `pv_dynamic_confidence` (factor_today), `pv_actual_today_kwh`, `pv_baseline_elapsed_kwh`, `pv_dynamic_active`, `pv_solcast_confidence` (если применимо), `pv_baseline_today_kwh` (общий ожидаемый baseline на сегодня). Эти же поля прокидываются в `ScheduleData` API карточки.
- Карточка отображает PV Confidence в двух местах: компактный цветной индикатор в `status-bar` (зелёный/жёлтый/красный по порогам) и подробный блок в `stats-tab` (фактор, actual/forecast elapsed, флаг активности). Индикатор скрывается если динамика неактивна и статичный slider = 100% (нечего показывать).
- Реактивность остаётся за существующим `OPTIMIZE_INTERVAL` — частоту пересчёта пользователь регулирует сам (hourly/reactive).
- Метки новых полей конфига добавляются в `strings.json` и `translations/` (en/ru — что есть в проекте).
- На reload интеграции кэш факторов сбрасывается, чтобы атрибуты не показывали стейл до первого пересчёта.
- README предупреждает о компаундировании со встроенным `dampening` Solcast HA-интеграции: если пользователь настроил dampening_factor в самом Solcast, наш slider лучше оставить на 100%, иначе занижение перемножается.
